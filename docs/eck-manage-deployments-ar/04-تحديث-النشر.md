# 4 — تحديث النشر (تعديل بدون إعادة بناء من الصفر)

**الرابط الرسمي:**  
<span dir="ltr">https://www.elastic.co/docs/deploy-manage/deploy/cloud-on-k8s/update-deployments</span>

## الفكرة

بعد النشر الأول، **لا تحذف الكلاستر** لكل تغيير. تعدّل ملف المواصفة (أو قيم Helm) ثم:

```bash
kubectl apply -f ...
```

المشغّل يحاول تطبيق التغيير **بأقل اضطراب** للكلاستر الحالي.

## ما الذي يمكن تغييره؟

- **معظم** عناصر المواصفة الأصلية، طالما التغيير مسموح في Kubernetes تحتها.
- مثال شائع: زيادة عدد النودز بتغيير <span dir="ltr">nodeSets[].count</span>.

```yaml
nodeSets:
- name: default
  count: 3   # كان 1
```

## ما الذي لا يمكن (أو صعب) تغييره؟

- **تصغير** حجم <span dir="ltr">PersistentVolumeClaim</span> بعد الإنشاء — Kubernetes لا يسمح عادة.
- بعض الحقول غير قابلة للتعديل (مثل <span dir="ltr">clusterIP</span> لخدمة — تغييره يعني حذف وإعادة إنشاء الخدمة).

راجع في التوثيق: **Updating Volume Claims**.

## ماذا تحتاج من موارد الكلاستر؟

قبل التوسع أو الترقية تأكد من:

- مساحة تخزين إضافية إن زدت النودز أو الحجم.
- **RAM و CPU** كافيان — أثناء التحديث قد تعمل pods جديدة **بجانب** القديمة لفترة.

## كيف تتابع التطبيق؟

1. لوجات مشغّل ECK.
2. <span dir="ltr">kubectl get events</span>
3. لوجات pods المنتج (<span dir="ltr">Elasticsearch</span> / <span dir="ltr">Kibana</span>)

إما ينجح التحديث أو تظهر رسالة تساعد في التشخيص.

## الفرق بين «تحديث» و«ترقية إصدار»

| | تحديث النشر (هذا الفصل) | ترقية الإصدار |
|---|-------------------------|----------------|
| أمثلة | زيادة <span dir="ltr">count</span>، تغيير <span dir="ltr">resources</span>، إعدادات | تغيير <span dir="ltr">spec.version</span> من 8.x إلى 9.x |
| الملف | هذا الملف | [11-ترقية-الإصدار.md](./11-ترقية-الإصدار.md) |

كثير من التغييرات تستخدم نفس الأسلوب (`apply`)، لكن ترقية الإصدار لها تخطيط وتوافق إصدارات ECK.

## صيغة YAML والتغييرات

للقواعد العامة لكتابة التعديلات في المانيفست، التوثيق يحيلك لنفس صفحة **Update your deployments** وإلى **Configure deployments**.
